В 7 версії з'явились агентні
Так, у Vercel AI SDK 7 агентні можливості розширилися. Уточнення: ToolLoopAgent уже був у v6; v7 додала, зокрема, контекст інструментів, політики підтвердження та WorkflowAgent для виконання з відновленням. 

Для твого CV Builder можна зробити одного агента з Claude, який має інструменти:

getSourceFacts — отримати факти з початкового CV та відповідей користувача;
proposeCvPatch — запропонувати зміни конкретних полів;
proposeQuestions — сформувати питання щодо відсутніх даних.
NestJS перевіряє та зберігає результат, контролює доступ користувача й стан завдання. Питання зберігаються в базі; відповідь користувача запускає наступний виклик агента.

Я б обмежив кількість кроків і дозволив агенту пропонувати зміни лише за визначеною схемою. Водночас Zod перевіряє структуру, але не правдивість: для нових тверджень потрібне посилання на початкові дані або відповідь користувача.

Тоді фіксуємо: React + NestJS + PostgreSQL + Prisma + Vercel AI SDK 7 + Claude.

Один агент із чіткими інструментами, збереження прогресу в базі та уточнення відсутніх фактів через питання користувачу.

Наступний крок — визначити моделі даних і REST endpoints, щоб мати конкретний план реалізації в межах 10 годин.

Саме prism Чи drizzle
Для цього тестового я б обрав Prisma. Ти маєш лише 10 годин, а основна складність — AI-флоу, відновлення генерації та редагування CV.

Prisma	Drizzle

Моя рекомендація: Prisma для CRUD і зв’язків, а складний запит отримання фонового завдання — параметризованим SQL за потреби.

Якщо досвід з обома однаковий — бери Prisma. Якщо Drizzle вже знайоміший — він теж повністю підходить, переходити заради тестового немає сенсу.

Drizzle цікавий і явний варіант
Тоді обираємо Drizzle + PostgreSQL. Явні SQL-запити добре пасують до фонового обробника: отримання завдання, блокування від одночасної обробки та відновлення після збою.

Фіксуємо стек: React + NestJS + Drizzle + PostgreSQL + Vercel AI SDK 7 + Claude.

Для бази достатньо п’яти таблиць:

users — облікові записи;
cvs — поточний документ, цільова роль, версія;
cv_sources — початковий текст і факти від користувача;
cv_questions — уточнення та відповіді;
generation_jobs — статус, спроби, помилка та час блокування.
Сам CV можна зберігати в JSONB, а власника, статуси й зв’язки — у звичайних колонках. Структуру документа перевірятиме Zod.

Напогана структура бд
Так, залишаємо її як основу. Я б одразу заклав три важливі деталі:

cvs.version — щоб результат генерації не перезаписав ручні зміни, зроблені під час її виконання.
generation_jobs.locked_until — щоб після збою завдання можна було повторно взяти в обробку.
cv_questions.field_path — щоб знати, яке поле уточнює питання, наприклад experience.<id>.startDate.
Для елементів досвіду й освіти в JSONB варто використовувати стабільні ID, щоб перестановка блоків не ламала прив’язку питань.

Це невелика схема, але вона вже покриває головні ризики тестового.

А в яких статусах може бути резюме щоб тримати це як стецт машина
Я б розділив стан резюме та стан фонового завдання. Тоді помилка повторної генерації не робить уже готове CV «зламаним».

Під час генерації статус CV залишається попереднім. UI показує прогрес за активним generation_jobs.status:

Статус завдання	Значення
pending	Очікує обробки
processing	Виконується
completed	Результат успішно застосовано
failed	Завершилось помилкою
superseded	Результат застарів через новішу версію CV
Основні переходи: pending → processing → completed / failed / superseded. Після втрати блокування processing → pending, якщо ліміт спроб ще не вичерпаний.

Відповідь на питання сама по собі не переводить CV у ready — спочатку треба застосувати уточнення до документа. Ручне редагування та завантаження PDF теж не потребують окремих статусів. ready означає готовність до перегляду й використання, а не гарантію правдивості всіх тверджень.

П як буде відбуватись редагування і як бібліотека чи технології для pdf
Редагуємо структуровані дані CV у React, а PDF генеруємо з них. Це дає просте збереження, ручні зміни та уточнення через AI.

На комп’ютері: зліва форма, справа попередній перегляд. На телефоні — вкладки «Редагування» і «Перегляд».

Користувач може змінити:

контакти та summary;
посади, компанії, дати й окремі bullet points;
освіту та навички;
порядок блоків, додати або видалити запис.
Для MVP вистачить звичайних полів і textarea. Кнопка «Зберегти» надсилає документ із його версією:

PATCH /cvs/:id
{
  "version": 3,
  "document": {
    "contact": {},
    "summary": "...",
    "experience": [],
    "education": [],
    "skills": []
  }
}

NestJS перевіряє власника, структуру та версію. Якщо документ уже змінився — повертає 409 Conflict. Так само результат AI застосовується лише до тієї версії, з якої починалася генерація.

Для PDF я б обрав @react-pdf/renderer. Він генерує PDF через React-компоненти в браузері та Node.js, зокрема у вигляді потоку або буфера. Тобто шаблон можна винести у спільний пакет і використовувати для перегляду та серверного експорту. 

Варіант	Перевага	Що врахувати
@react-pdf/renderer	Один PDF-шаблон для frontend і backend	Власні компоненти Page, View, Text, обмежений набір стилів
Puppeteer	Верстка через HTML/CSS і друк у PDF	Потрібен Chromium у Docker
Puppeteer підтримує друк із CSS для сторінки та налаштування формату й фону. Це хороший варіант, якщо хочеш верстати шаблон звичайним HTML. 

Для твого тестового пропоную:

Один шаблон CvPdfDocument, формат A4.
Локально включений шрифт із кирилицею — renderer підтримує реєстрацію шрифтів. 
GET /cvs/:id/pdf генерує PDF із збереженої версії CV.
Перед завантаженням UI зберігає незбережені зміни.
Перевіряємо довге CV: переноси сторінок, кирилицю та можливість виділити й скопіювати текст.
AI повертає лише дані. Дизайн, розміщення блоків і PDF контролює наш шаблон.
