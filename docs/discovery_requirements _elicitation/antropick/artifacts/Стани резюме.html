Стани резюме

Шість станів від моменту, коли користувач натиснув «Згенерувати», до готового резюме. Один і той самий список для бекенду й фронтенду: бекенд зберігає стан і віддає його в API рядком, фронтенд лише показує.

Як стани змінюють один одного

Що відбувається в кожному стані

queued

У черзі

далі: generating
Бекенд

Вихідний текст і задачу збережено в базі, id лежить у черзі. Рахує, скільки задач попереду.

Фронтенд

Бейдж і рядок «перед вами N». Опитує статуси кожні 3 секунди.

Дії користувача

Видалити резюме. Можна закрити сторінку, задача не зникне.

generating

Генерується

далі: needs_input, ready, retrying, failed
Бекенд

Воркер збирає промпт, викликає Claude, перевіряє відповідь схемою і звіряє факти з вихідним текстом. Чернетку, питання і новий стан пише однією транзакцією.

Фронтенд

Індикатор роботи й назва етапу. Опитування триває. Редактора ще немає.

Дії користувача

Видалити резюме.

retrying

Повтор після збою

далі: generating
Бекенд

Спроба не вдалася: мережа, таймаут або невалідна відповідь моделі. Задача чекає паузу й повертається у воркер, лічильник спроб зростає.

Фронтенд

Рядок «Збій, спроба 2 з 3». Опитування триває.

Дії користувача

Видалити резюме. Більше нічого робити не треба.

failed

Помилка

далі: queued
Бекенд

Усі три спроби вичерпано. Зберігає зрозумілий текст помилки. Вихідний текст лишається, тож повтор не вимагає завантажувати файл знову.

Фронтенд

Текст помилки і кнопка «Повторити». Опитування зупинено.

Дії користувача

Повторити генерацію або видалити резюме.

needs_input

Потрібні відповіді

далі: ready
Бекенд

Чернетка збережена, є відкриті питання. Кожна відповідь оновлює своє поле резюме. Коли відкритих питань не лишилося, ставить ready.

Фронтенд

Редактор, список питань з лічильником, PDF. Опитування зупинено.

Дії користувача

Відповісти, обрати варіант, пропустити питання, редагувати поля, завантажити PDF.

ready

Готове

кінцевий стан
Бекенд

Чернетка збережена, відкритих питань немає: на всі відповіли або їх пропустили. PDF збирає з поточних даних під час кожного завантаження.

Фронтенд

Редактор і PDF. Блоку питань немає.

Дії користувача

Редагувати поля, завантажити PDF, видалити резюме.

Спільний код для бекенду і фронтенду

export const CV_STATUSES = [
  'queued', 'generating', 'retrying', 'failed', 'needs_input', 'ready',
] as const;
export type CvStatus = (typeof CV_STATUSES)[number];

// дозволені переходи: бекенд перевіряє їх перед кожною зміною стану
export const CV_TRANSITIONS: Record<CvStatus, CvStatus[]> = {
  queued:      ['generating'],
  generating:  ['needs_input', 'ready', 'retrying', 'failed'],
  retrying:    ['generating'],
  failed:      ['queued'],
  needs_input: ['ready'],
  ready:       [],
};

export const isInProgress = (s: CvStatus) =>
  s === 'queued' || s === 'generating' || s === 'retrying';   // фронтенд опитує статуси
export const hasDraft = (s: CvStatus) =>
  s === 'needs_input' || s === 'ready';                       // доступні редактор і PDF

Стан обчислює тільки бекенд. Фронтенд його не виводить із власних даних, а зіставляє рядок із підписом, кольором і набором кнопок. Так обидві сторони не розійдуться.

Що станом не є

  • Форма до надсилання. Запису в базі ще немає, незавершений ввід живе тільки в браузері.
  • Етапи всередині генерації. Збирання промпту, відповідь моделі, перевірка і збереження йдуть окремим полем stage і потрібні лише для підпису на екрані.
  • Ручне редагування. Зберігає нову версію даних, стан лишається тим самим.
  • Завантаження PDF. Файл збирається на льоту з поточних даних і ніде не зберігається.
  • Видалення. Запис просто зникає, стану «видалено» немає.
