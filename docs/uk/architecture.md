## 1. Продукт в одному абзаці

Автентифікований користувач створює CV **під позицію**. Назва позиції обов'язкова
("Senior Backend Engineer"); необов'язкова коротка нотатка про позицію (рівень, стек, домен,
що важливо) уточнює summary, порядок досвіду та подання **match**. Користувач обирає
**мову CV** (за замовчуванням англійська) і надає свій досвід як PDF або вільний текст
будь-якою мовою. Фонова задача перетворює його на структуровану чернетку, у якій кожен факт
можна простежити до джерела або до власних відповідей користувача; усе відсутнє, розмите чи
непідтверджене стає питанням. Користувач відповідає, редагує будь-яке поле, бачить, наскільки CV
покриває вимоги ролі, і завантажує PDF формату A4 з текстом, який можна виділяти, — з телефона
чи комп'ютера, а згодом і з будь-якого пристрою.

### Примітки щодо обсягу

- **Нотатка про роль vs. "адаптація під опис вакансії" (поза обсягом за специфікацією).** Ми
  приймаємо необов'язковий вільний текст про роль — коротку нотатку або вставлену вакансію — і
  використовуємо його лише для того, щоб (a) сфокусувати summary/порядок і (b) вивести список
  вимог ролі для подання match. Він ніколи не є джерелом фактів про людину: ніщо з нього не
  потрапляє в CV інакше, ніж через питання, на яке відповів користувач. Без нього CV генерується
  так само. (У цьому наборі документів поле ще називається `roleNote`, ≤ 1 000 символів;
  перейменування на `roleContext` і ліміт 5 000 з'являться разом зі схемами API.) README явно фіксує цю межу.
- **Match — це підказка, а не вердикт.** Модель перелічує, що потрібно *ролі*; чи покриває це
  *CV*, обчислює наш код (збіг за ключовими словами), а не вигаданий моделлю відсоток.
- Один шаблон PDF, без OAuth/скидання пароля/підтвердження email/платежів/адмінки (специфікація).

## 2. Користувацький сценарій

```
 реєстрація / вхід
       │
       ▼
 My CVs ── New CV ─────────────────────────────────────────────────────────────┐
   ▲         назва ролі* + нотатка про роль (опц.) + мова CV (типово англ.)    │
   │         + досвід: текст або PDF                                           │
   │         (PDF → сервер витягує текст → користувач перевіряє його в полі)   │
   │         └─ POST /api/cvs → 202, перехід на /cvs/:id                       │
   │                                                                           ▼
   │      /cvs/:id  queued → generating → (retrying) ──────────────▶ failed ── Retry
   │                  "2 ahead of you" · "Checking facts…" · "attempt 2 of 3"
   │                                     │
   │                                     ▼
   │      needs_input / ready: редактор · питання · match · прев'ю · Download PDF
   │         відповідь / пропуск → поле оновлено, match перераховується наживо
   │         правка + Save (оптимістична версія) · "Also fits: X" → нове CV, те саме джерело
   └──────── назад до списку (опитування показує, як паралельно просуваються інші CV)
```

## 3. Компоненти та розгортання

```
                ┌───────────────┐ той самий origin /api (httpOnly JWT)   ┌──────────────────┐
 телефон / ПК ─▶│ web           │ ─────────────────────────────────────▶ │ api (NestJS)     │
                │ nginx: SPA +  │ ◀── опитування /api/cvs/statuses 3 с   │ HTTP, без LLM,   │
                │ проксі /api   │                                        │ крім відповідей* │
                └───────────────┘                                        └──┬────────┬──────┘
                                                                   Drizzle │        │ в чергу
                                                                           ▼        ▼
                                                                 ┌──────────┐  ┌────────┐
                                                                 │ postgres │  │ redis  │
                                                                 │ джерело  │  │ лише   │
                                                                 │ істини   │  │ BullMQ │
                                                                 └────▲─────┘  └───┬────┘
                                                                      │  Drizzle   │ споживає
                                                                 ┌────┴────────────▼──────┐
                                                                 │ worker (той же образ,  │──▶ Anthropic API
                                                                 │ worker.ts, без HTTP)   │    (AI SDK v7)
                                                                 └────────────────────────┘
```

- **web** — збірка Vite, яку віддає nginx; nginx також проксіює `/api` на `api`, тож cookie є
  first-party і CORS не потрібен. У dev те саме робить проксі Vite.
- **api** — автентифікація, CRUD для CV, прийом/експорт PDF, питання, постановка в чергу.
  Запускає міграції під час старту. Усередині запиту LLM не викликається.
- **worker** — та сама кодова база й Docker-образ, точка входу `worker.ts`
  (`NestFactory.createApplicationContext`), завантажує лише процесор BullMQ та агентів.
- **postgres** — єдине джерело істини: користувачі, CV, статуси, питання, спроби.
- **redis** — лише транспорт черги. Його втрата не призводить до втрати даних: під час старту
  worker знову ставить у чергу незавершені CV (див. [cv-statuses.md §4](cv-statuses.md#4-як-змінюється-статус)).

`docker compose up` запускає `web`, `api`, `worker`, `postgres`, `redis`. Усі контейнери працюють
в UTC. Єдиний секрет — `ANTHROPIC_API_KEY` (`.env`, див. `.env.example`).

**Кожен підпроєкт запускається й окремо.** `backend/` і `frontend/` мають власні `Dockerfile` і
`compose.yaml`; кореневий `compose.yaml` лише підключає обидва через `include`, тож кожен сервіс
описаний один раз. Образи збираються з коренем репозиторію як контекстом, бо їм потрібні
`shared/` і lockfile workspace.

| режим | сервіси | куди web проксує `/api` |
|---|---|---|
| весь стек (кореневий `compose.yaml`) | web, api, worker, postgres, redis | `api:3000` (задано в `compose.stack.env`) |
| лише backend (`backend/compose.yaml`) | api, worker, postgres, redis | — |
| лише frontend (`frontend/compose.yaml`) | web | `host.docker.internal:3000` (backend на хості) |

nginx резолвить `API_UPSTREAM` на кожен запит через DNS Docker, тож web стартує раніше за api і
переживає його перезапуск. Порядок старту: postgres і redis healthy → api (виконує міграції;
healthy, коли відповідає `GET /api/health`) → worker.

**Чому черга:** [backend/docs/adr/0001](../../backend/docs/adr/0001-queue-in-redis-status-in-postgres.md).
**Чому опитування (polling), а не SSE/WebSocket:** [docs/adr/0001](../adr/0001-poll-statuses-not-push.md).

## 6. Пайплайн генерації

### 6.1 Модель даних (Postgres, Drizzle)

Postgres зберігає користувачів, CV (джерело, факти користувача, статус, чернетку, вимоги,
версію), питання та по одному рядку на кожну спробу генерації. Таблиці й колонки:
`backend/docs/architecture.md` §2.

### 6.2 `CvData` (shared/cv-data.ts)

```ts
CvData = {
  contacts: { fullName, email, phone, location: string | null; links: string[] /* ≤5 */ },
  summary: string | null,                                   // 2–4 речення, під цільову роль
  experience: { id, title, company, period: string | null;  // ≤10, найрелевантніше першим
                bullets: string[] /* ≤12 × ≤400 */ }[],
  projects:   { id, name, period, url: string | null; bullets: string[] }[],   // ≤6
  education:  { id, institution, degree, period: string | null }[],            // ≤6
  certifications: { id, name, issuer, year: string | null }[],                 // ≤10
  skills: string[],                                         // ≤40 × ≤60, без мов
  languages:  { id, name, level: string | null }[],         // ≤8
  sectionOrder: MovableSection[],                           // сім блоків під контактами
}
```

- **Вісім блоків**: п'ять зі специфікації плюс Projects, Certifications і Languages. Курси,
  нагороди, публікації, волонтерство та інтереси — не блоки.
- **Будь-яке поле може бути порожнім** — модель не має права його вигадувати, — тому схема нічого
  не вимагає. Що в CV *має бути*, визначає окреме правило — `findMissing` у
  `shared/cv-missing.ts`:

  | блок | обов'язковий | якщо порожній |
  |---|---|---|
  | contacts: `fullName` і принаймні одне з `email` / `phone` | так | питання на кожне відсутнє поле |
  | summary | так | питання |
  | skills | так | питання `multi` (§6.5) |
  | experience | так, але «немає досвіду» дозволено | питання, яке можна пропустити |
  | education, projects, certifications, languages | ні | блоку немає, питання немає |

  Усередині наявного запису порожні `title` / `company` / `period` (досвід) або `institution`
  (освіта) теж вважаються відсутніми. Відсутній блок чи поле позначається в редакторі та
  перелічується біля кнопки PDF; завантаження це ніколи не блокує.
- **Порядок блоків** — частина чернетки: `sectionOrder` містить сім рухомих блоків, кожен рівно
  один раз (інше відхиляється). Contacts завжди перший. Нова чернетка отримує фіксований порядок
  за замовчуванням — summary, experience, projects, education, certifications, skills, languages;
  модель його не обирає, а користувач переставляє блоки в редакторі.
- Записи мають UUID-id, унікальні в межах чернетки (для згенерованої чернетки їх призначає
  сервер, для записів, доданих у редакторі, — клієнт), тож питання й правки переживають зміну
  порядку. Буліти й навички — прості рядки: ніщо не посилається на окремий буліт.
- Порожнє = відсутнє: `null`, `""`, `[]` не рендеряться ні в прев'ю, ні в PDF, а блок, у якому
  нічого немає, не має заголовка (`isSectionEmpty`). Записи, у яких порожні всі поля,
  відкидаються під час збереження разом із порожніми булітами, навичками й посиланнями
  (`dropEmptyItems`).
- Ліміти довжини (`CV_LIMITS`): 200 символів для короткого поля (ім'я, посада, компанія, період,
  рівень…), 300 для посилання, 2 000 для summary — на додачу до кількостей вище.
- Дати, роки й рівні мов лишаються в тому вигляді, як у джерелі ("2019 – present", "fluent");
  нормалізація вигадала б точність. Для мови без рівня модель має поставити питання `choice`
  (A1–C2, Native); це не обов'язкове поле, тож авто-питання його не дублює.
- CV пишеться мовою, обраною під час створення (§6.7), незалежно від мови джерела.

### 6.3 Прийом даних

1. **PDF** (необов'язковий крок): `POST /api/ingest/pdf` (multipart) — ≤ 5 МБ, магічні байти `%PDF`,
   ≤ 10 сторінок, текст витягується за допомогою unpdf; < 50 символів тексту ⇒ `422 PDF_UNREADABLE`
   ("схоже на скан — вставте текст"). Повертає текст; **нічого не зберігається**. Фронтенд вставляє
   його в текстове поле, щоб користувач бачив і міг виправити саме те, що читатиме модель.
2. **Створення**: `POST /api/cvs` (JSON) — роль, нотатка, `sourceText` (80–20 000 символів) або `fromCvId`.
3. Перевіряються ліміти (§9), потім одна транзакція вставляє CV (`queued`) і рядок задачі, після
   чого задача ставиться в чергу. Відповідь `202` із CV. Якщо постановка в чергу не вдалася, рядок
   лишається `queued`, і його підхоплює відновлення під час старту worker.

### 6.4 DraftAgent — tool loop на AI SDK v7

Worker запускає **DraftAgent**: один tool loop на AI SDK v7 з єдиним інструментом, що валідує,
— `submit_draft`. Одна подача містить чернетку, цитати-докази з джерела, до 7 питань, до 12 вимог
(§7) і до 3 запропонованих ролей. Зворотний зв'язок верифікатора дає моделі до 3 кроків, щоб
виправити свої твердження; те, що й далі не проходить, стає питанням (§6.6). Результат
зберігається однією транзакцією, і CV переходить у `needs_input` або `ready`. Промпт, схема
інструмента, кроки й тайм-аути: `backend/docs/architecture.md` §3.

### 6.5 Питання та відповіді

Типи питань (як у прототипі):

| kind | origin | UI | після відповіді |
|---|---|---|---|
| `confirm` | verifier | цитоване твердження + "Yes, add it" / "No" | так → твердження додається до своєї цілі (буліт/навичка); ні → відкидається |
| `multi` | verifier + match | чипи-перемикачі + "Other, comma-separated" | позначені пункти додаються до `skills` (без дублікатів) |
| `choice` | model | чипи + "Other" з полем вводу | значення записується в ціль |
| `text` | model / auto | поле вводу | значення записується в ціль |

- `choice` — лише там, де набір відповідей загальний (рівень англійської, тип зайнятості, розмір
  команди), і ніколи для вгаданих моделлю фактів ("3 / 5 / 7 years").
- **Авто-питання** (детерміновані, `buildAutoQuestions`) для всього, що повертає `findMissing`
  (§6.2): обов'язкові блоки та обов'язкові поля наявних записів — якщо модель уже не запитала про
  це поле. Питання про досвід можна пропустити («немає досвіду»).
- **Одне питання `multi`** "Which of these have you worked with? Only what you tick goes into the
  CV" — варіанти = навички, які модель записала, але джерело не підтверджує, ∪ вимоги типу `skill`,
  не покриті CV (§7), максимум 8. Варіанти формує наш код, а не модель.
- Обмеження: ≤ 12 відкритих питань на CV; ≤ 5 `confirm`; ≤ 7 від моделі. `text`, `choice`, `multi`
  можна пропустити; на `confirm` відповідають так/ні.
- Ціль має вказувати на наявне поле, інакше питання відкидається.

Потік відповіді (`POST …/answer`, синхронно, в API):

1. Право власності, CV у статусі `needs_input`, питання `open`, відповідь ≤ 1 000 символів і
   відповідає своєму типу.
2. `applyAnswer` (чиста): скалярні цілі (contacts, `period`, `degree`, …) записуються напряму;
   для цілей у `skills` додається `"{label}: {value}"` (напр. "English: B2"); для цілей
   `summary`/`bullets` відповідь додається як речення/буліт.
3. Одна транзакція: оновити `data`, додати `{question, answer}` до `facts`, питання → `answered`,
   `version + 1`; якщо відкритих питань не лишилося → `ready` (CAS). Повертає повне CV.

Фронтенд зберігає незбережені правки **перед** надсиланням відповіді (поведінка з прототипу), тож
відповідь ніколи не перезаписує локальні правки і не перезаписується ними.

AnswerAgent, що переписує summary або пункт з урахуванням відповіді, спроєктували й вирізали
(§13, рядок 5): відповідь потрапляє в CV як є. README згадує його в розділі «що зробили б, маючи
більше часу».

### 6.6 Як не дати AI вигадувати факти

Кожен *факт* у CV має простежуватися до `source_text` або `facts`. Сервер перевіряє кожну
частину чернетки щодо джерела — текст через цитати-докази мовою джерела, числа, контакти й назви
технологій напряму — і все, що не пройшло, видаляється або очищується й стає питанням (`confirm`
для пункту, `multi` для навички, `text` / `choice` для поля). `verification` зберігає лічильники,
які показує UI («12 пунктів підтверджено цитатами з вашого тексту, 2 надіслано вам на
підтвердження, 1 навичку перенесено в пропозиції»). Правила для кожного поля:
`backend/docs/architecture.md` §4.

### 6.7 Мова CV

- Обирається на екрані New CV у нативному `<select>` (combobox), **за замовчуванням англійська**;
  надсилається як `language` у `POST /api/cvs`, зберігається в `cvs.language`, незмінна. CV "для
  іншої ролі" (`fromCvId`) отримує попередньо обрану мову батьківського CV, яку можна змінити.
- Allow-list `CV_LANGUAGES` у `shared/src/cv-language.ts` — один запис на мову: код, англійська
  назва (для промпта), власна назва мови (для select), заголовки розділів (прев'ю + PDF) і шаблони
  авто-питань. Початковий список: `en` English, `uk` Українська, `pl` Polski, `de` Deutsch,
  `fr` Français, `es` Español. Додати мову = додати один запис. Обмежено писемностями, які покриває
  вбудований Liberation Sans (латиниця, кирилиця, грецька); для CJK/арабської потрібен інший шрифт.
- Сервер приймає лише коди зі списку (інакше `400`) і підставляє в `<cv_language>` **англійську
  назву зі списку**, а не текст користувача, — поверхні для ін'єкцій немає.
- **Слідують за мовою CV:** увесь текст CV; тексти питань від моделі та авто-питань (щоб відповіді
  надходили тією самою мовою); назви вимог (ключові слова містять терміни мовою CV та англійські
  назви технологій, §7); заголовки розділів у прев'ю та PDF.
- **Не слідують:** UI (англійською), повідомлення про помилки, джерело (будь-якою мовою). Назви
  компаній і навчальних закладів зберігають написання з джерела, якщо тільки саме джерело не
  наводить назву мовою CV.
- Відповіді іншою мовою вставляються як є.

## 7. Цільова роль і match

- **Вхідні дані:** `target_role` (обов'язкова), `role_note` (необов'язкова). Обидві незмінні в
  межах CV — summary і порядок згенеровано саме під них. Інша роль = інше CV.
- **Вимоги** надходять від DraftAgent у тому самому виклику: до 12 `{label, kind, keywords}`
  ("PostgreSQL" · skill · ["postgres", "postgresql"]; "Team leadership" · experience · ["led",
  "mentored", "team lead"]). Вони описують роль, тому їх не звіряють із джерелом — лише обмежують.
  Назви — мовою CV; ключові слова — мовою CV плюс англійські назви технологій, бо їх зіставляють
  із текстом CV.
- **Match** = `computeMatch(data, requirements)` у `shared/match.ts`: вимога вважається *покритою*,
  якщо будь-яке ключове слово трапляється (після нормалізації, з урахуванням меж слів) у summary,
  посадах, булітах чи навичках CV. Результат: `{ covered, total, items: [{ id, label, kind, covered, foundIn }] }`.
  - Виконується **в браузері при кожній правці** (відкладено) — відповідь "PostgreSQL ✓" чи
    введений буліт одразу робить вимогу зеленою, без запиту і без LLM.
  - Виконується на бекенді після чернетки, щоб сформувати питання `multi` з непокритих вимог
    типу `skill`.
- **UI:** смуга "Covers 7 of 10 requirements" у шапці CV; вкладка Match перелічує покриті (із
  зазначенням, де знайдено) та відсутні вимоги; для відсутніх вимог типу `experience` показується
  "Add it in the editor if it's true" — вони ніколи не вставляються автоматично.
- **Запропоновані ролі:** чипи "Also fits: Node.js Tech Lead" → `/cvs/new?fromCvId=…&role=…` →
  `POST /api/cvs { fromCvId, targetRole }` копіює `source_text` + `facts`; враховується в лімітах.

## 8. Обробка збоїв

Генерація повторює тимчасові помилки моделі (3 спроби з backoff), одразу завершується невдачею
на тих, що не варто повторювати, переживає падіння worker і стертий Redis, відкидає результат для
видаленого CV; застарілі правки отримують `409 VERSION_CONFLICT`, пошкоджена збережена чернетка —
`500 DATA_CORRUPT`. Повна таблиця: `backend/docs/architecture.md` §5. З боку фронтенду: невдалий
запит показує Retry, невдала мутація — помилку поруч із кнопкою, `401` повертає на логін.

## 9. Автентифікація, ізоляція та ліміти

- Сесія — JWT у cookie з `httpOnly`, яку ставлять signup/login; однакова помилка для невідомого
  email і неправильного пароля.
- Кожне CV належить одному користувачу; чуже CV ⇒ `404`, а не `403`.
- Ліміти: 10 генерацій/користувача/годину, ≤ 2 у процесі на користувача, 60 відповідей/годину,
  ingest 20/хв → `429` + `Retry-After`. Генерація — це те, що запустив користувач: створення CV
  або ручний Retry; автоматичні повтори невдалої спроби не рахуються.
- Відомі спрощення (README): JWT не можна відкликати до закінчення строку; signup показує, що
  email зайнятий; гонку «порахувати, потім вставити» в лімітах прийнято.
- Як це забезпечується: `backend/docs/architecture.md` §6.

## 10. Експорт у PDF

`GET /api/cvs/:id/pdf` рендерить на сервері зі **збережених** `data`: A4, справжній текст ⇒
його можна виділити. Верстка з прототипу: ім'я 20 bold; рядок контактів, з'єднаний через " · ";
заголовки розділів 9 pt bold великими літерами з лінією, текст береться з
`CV_LANGUAGES[cv.language]` ("Experience" / "Досвід"). Спершу контакти (email, телефон,
місцезнаходження, посилання), далі блоки в порядку `data.sectionOrder`:

| блок | рядок заголовка | приглушений рядок | нижче |
|---|---|---|---|
| summary | — | — | один абзац |
| experience | "Title, Company" | період | буліти |
| projects | назва | "період · url" | буліти |
| education | "Institution, Degree" | період | — |
| certifications | "Name, Issuer" | рік | — |
| skills | — | — | один абзац через ", " |
| languages | — | — | один абзац: "Name (Level)" через ", " |

Буліти "•" з відступом 14 pt. Порожні поля/блоки пропускаються, як і роздільник біля відсутньої
частини ("Title", а не "Title, "). Ім'я файлу = санітизована назва. Як це малюється (pdfkit,
шрифти, поля, сторінки): `backend/docs/architecture.md` §7.

Прев'ю в застосунку — HTML-"аркуш" (пропорції A4, ті самі шрифти й розміри в одиницях
container query), що рендериться з **незбережених** значень форми; Download спершу зберігає, а
потім завантажує PDF із сервера.

## 11. Фронтенд

### Маршрути (React Router data mode, кожен екран — lazy-loaded)

| шлях | екран | loader |
|---|---|---|
| `/login`, `/signup` | форма автентифікації | редирект на `/`, якщо вже ввійшли |
| `/` | My CVs | захищений лейаут: `ensureQueryData(me)` → 401 ⇒ редирект на `/login?next=…` |
| `/cvs/new` | New CV (`?fromCvId=&role=` попередньо заповнюють форму для запропонованих ролей) | |
| `/cvs/:cvId` | CV — вміст залежно від групи статусів | prefetch CV |
| `*` | Not found | |

URL — це стан навігації: глибокі посилання й кнопка «назад» працюють; перезавантаження на
`/cvs/:id` відновлює опитування.

### Шар даних

- `shared/api/client.ts`: обгортка над `fetch`, `credentials: 'same-origin'`, парсить кожну
  відповідь Zod-схемою з `shared/api.ts`, кидає `ApiError { status, code, message, details }`.
- Фабрики query options для кожної фічі (`cvQueries.list()`, `cvQueries.detail(id)`,
  `cvQueries.statuses(ids)`), ключі `['cvs', …]`, `['me']`.
- **Опитування:** список і сторінка CV запускають `statuses(id CV у процесі)` з
  `refetchInterval: 3000`, увімкнено лише поки цей список непорожній (також ставиться на паузу у
  фонових вкладках). Коли CV виходить із групи «у процесі» → інвалідувати `['cvs','list']` і
  `['cvs','detail',id]`. Повний JSON CV ніколи не опитується.
- Мутації повертають повне CV → `setQueryData`, без refetch. 401 на будь-який запит → очистити
  `['me']` → роутер перенаправляє на вхід.

### Екрани

- **Auth** — одна форма-картка + кроки "how it works" з прототипу (лише на десктопі).
- **My CVs** — рядки: назва, плашка статусу, кількість відкритих питань, match "7/10", час
  оновлення (`Intl.DateTimeFormat` у локалі пристрою); дії за групою статусів: Open / Watch
  progress / Retry / Delete (вбудоване двокрокове підтвердження). Порожній стан пояснює, що потрібно.
- **New CV** — назва ролі*, нотатка про роль (необов'язкова, з підказкою, що туди писати),
  **мова CV** (нативний `<select>` із власними назвами мов, за замовчуванням англійська — нативний
  select безкоштовно дає системний пікер телефона й повну доступність), текстове поле для досвіду
  з "Upload PDF" (→ прийом → з'являється текст, "Extracted 3 120 chars from 2 pages, check below")
  і лічильником символів; залишок генерацій на цю годину (`GET /api/usage`). Відправлення →
  `/cvs/:id`. Невідправлена форма автозберігається в `sessionStorage`.
- **CV** —
  - *у процесі:* плашка статусу, текст етапу / "N ahead of you" / "attempt 2 of 3", невизначений
    індикатор прогресу, "You can close this page". `aria-live="polite"`.
  - *failed:* текст помилки, Retry, Delete.
  - *є чернетка:* шапка (назва, роль, смуга match, запропоновані ролі, Download PDF); **редактор**
    (усі вісім блоків; записи з кнопками вгору/вниз/видалити/додати; блоки під контактами з
    кнопками вгору/вниз; навички як чипи; буліти — одне текстове поле, по одному на рядок;
    відсутні обов'язкові блоки позначені); вкладки бічної панелі **Questions · N** /
    **Match** / **Preview**; липка **панель збереження**, коли є зміни (Cancel / Save); повідомлення
    зі звітом верифікації; повідомлення про конфлікт.

### Лейаут

- **≥ 980 px:** дві колонки — редактор ліворуч (`1.08fr`), бічна панель праворуч (`.92fr`) із
  вкладками Questions / Match / Preview.
- **< 980 px:** одна колонка, сегментований перемикач **Edit · Questions N · Match · Preview**;
  одна панель за раз; панель збереження прилипає донизу з `env(safe-area-inset-bottom)`.
- Mobile first: сенсорні цілі ≥ 40 px, шрифт полів вводу 16 px (без зуму в iOS), рядки списку
  складаються вертикально при ≤ 760 px.

### Стратегія рендерингу (без зайвих перерендерів)

- Редактор — одна форма RHF; `key={cv.id + ':' + cv.version}` перемонтовує її зі свіжими
  `defaultValues`, коли змінюється серверна версія (жодних ефектів синхронізації).
- Поля вводу некеровані (`register`); масиви — через `useFieldArray`; стан dirty читається лише
  всередині `SaveBar` через `useFormState` — введення тексту не перерендерює сторінку.
- `Preview` і `MatchPanel` підписуються через `useWatch` і рендерять з `useDeferredValue(values)`
  — введення лишається чуйним, а аркуш і match оновлюються трохи згодом.
- Панель питань і картка прогресу читають лише свій зріз через `select` у Query.
- Мемоізацію бере на себе React Compiler; правила — у `frontend/CLAUDE.md`.

### Дизайн-система

Належить фронтенду: `frontend/docs/design.md` (токени, скло, фон, примітиви, лейаути, стани) і
`frontend/docs/adr/`. Коротко: токени й шрифти з прототипу, лише світла тема, пастельний фон із
матовим склом тільки на плаваючих елементах керування (верхня панель, вкладки, панель
збереження, картка входу), власні примітиви, статус → тон (queued — neutral, generating —
accent, retrying і needs_input — wait, failed — bad, ready — ok).

Мова UI: англійська (див. §13). Дати й числа форматуються через `Intl` у локалі пристрою.
