# Decisions log — frontend first

Running record of the `/grill-with-docs` session (2026-10-05). Input for `/to-spec`; the design docs
(`docs/api.md`, `docs/architecture.md`, `docs/cv-statuses.md`, `docs/uk/`) are not updated yet.
Q numbers are the question numbers used in the session.

## Confirmed

### Order of work and mocks

- **Q1** Build order: `shared` (Zod schemas of `docs/api.md`, `cv-status.ts`, `cv-language.ts`,
  `computeMatch`) → frontend on mocks → backend.
- **Q2** Mocks are MSW handlers: the real API client, Zod parsing, error codes and polling run
  unchanged; the same handlers serve Vitest tests.
- **Q3** Mock mode is switched on explicitly (`pnpm dev:mock` / `VITE_API_MOCK=1`), never
  automatically when the backend is down, and is not part of the production image.
- **Q4** Mocks cover the whole flow: "database" in `localStorage` (reload loses nothing), a fake
  worker on timers (`queued` → `generating` with stages → `needs_input`), a fixture CV with
  questions of all four kinds, scenarios picked by a keyword in the target role (`fail`, `retry`,
  `ready`), limits and errors as in `docs/api.md`. The CV comes from a fixture, not from the typed
  text.
- **Q14** `GET /cvs/:id/pdf` in mock mode returns a static A4 file from fixtures.
- **Q5** First pass: auth, list, create (text + PDF), progress, failed/Retry, editor with Save and
  version conflict, questions, preview, PDF download. Second layer, separate tickets: Match panel,
  "Also fits" (`fromCvId`), `/api/usage`, `sessionStorage` autosave of the create form, dark theme.

### Open decisions of architecture.md §13

- **Q6** Confirmed: match by keywords in `shared`, no model score (2); `retrying` is its own status
  (3); the server extracts PDF text and the user reviews it before generation (4); AnswerAgent is
  designed but built last, answers are inserted as written until then (5); UI in English (7);
  explicit Save with a sticky save bar, unsaved edits are saved before an answer is sent (8).
- **Q6.1** The target role title is the main, required input. The role description is optional
  free text: a short note or a pasted vacancy. It is never a source of facts about the person; it
  only focuses the summary, the ordering and the requirements for Match.
- **Q21** The field is renamed `roleNote` → `roleContext` (UI label "About the role (optional)"),
  limit 5 000 chars so a vacancy text fits.

### API

- **Q7** `PATCH /api/cvs/:id` body is `{ version, title?, data? }`; at least one of `title` /
  `data` is required, otherwise `400`.
- **Q8** Ids of new experience/education/… items are generated by the client
  (`crypto.randomUUID()`); the server checks they are UUIDs and unique. One `CvData` schema for
  request and response.

### Questions and facts

- **Q9** Filling a field in the editor does not close an open question about it; a question closes
  only by answer or skip (as in the prototype).
- **Q13** Facts belong to one CV. They are reused when a new CV is created from it for another
  role (`fromCvId` copies source + facts) and by AnswerAgent. No "regenerate" action; `ready`
  stays final.

### CV structure

- **Q17.1** Eight blocks: Contacts, Summary, Experience, Education, Skills (task spec) plus
  Languages, Projects, Certifications. Courses, awards, publications, volunteering, interests are
  not separate blocks.
- **Q17.2** Schemas; every field may be empty because the model must not invent it:

  ```ts
  contacts:       { fullName, email, phone, location: string | null; links: string[] }   // ≤ 5 links
  summary:        string | null                                                          // 2–4 sentences
  experience:     { id, title, company, period: string | null; bullets: string[] }[]     // ≤ 10
  projects:       { id, name, period, url: string | null; bullets: string[] }[]          // ≤ 6
  education:      { id, institution, degree, period: string | null }[]                   // ≤ 6
  certifications: { id, name, issuer, year: string | null }[]                            // ≤ 10
  skills:         string[]                                                               // ≤ 40
  languages:      { id, name: string | null, level: string | null }[]                    // ≤ 8
  ```

  `level` is free text (a missing level becomes a `choice` question: A1–C2, Native, Other);
  `period` / `year` stay as source text; `skills` is a flat list without languages.
- **Q17.3** Required blocks: Contacts (`fullName` and at least one of `email` / `phone`), Summary,
  Skills, and Experience (required, but "no experience" is allowed — the question can be skipped).
  An empty required block produces a question and is marked "missing" in the editor. Education,
  Projects, Certifications and Languages are optional: empty means the block is absent, no
  question.
- **Q17.4** An empty required block never blocks the PDF download; a warning lists what is missing.
- **Q17.5** The user can change the order of blocks, not only of items inside a block. An empty
  block is not rendered in the preview or the PDF.
- **Q22** Block order is stored in the document: `data.sectionOrder` (each movable block exactly
  once, validated by the server); saved by the same PATCH under the same version.
- **Q23** Default order is fixed, not chosen by the model: Summary → Experience → Projects →
  Education → Certifications → Skills → Languages.

### Confirmed in the last round

- **Q24** Contacts is always the first block; the other seven are moved with up/down buttons.
- **Q10** Deleting an item that has an open question: the PATCH moves that question to `skipped`,
  and if it was the last open one the CV becomes `ready` (so PATCH can change the status — fix
  "Status unchanged" in `docs/api.md`). An answer to a question whose field is gone →
  `409 INVALID_STATE`.
- **Q11** Closed questions are collapsed under "Answered (N)" with the answer text; no
  re-answering — the field is corrected in the editor.
- **Q12** PDF download: with unsaved edits the button is "Save & download" and saves first (a
  failed save stops the download); then `fetch` → blob → `<a download>`, filename from
  `Content-Disposition`. The server renders the PDF from saved data. Errors are shown next to the
  button. Allowed in `needs_input` with a hint about open questions.
- **Q15** `POST /ingest/pdf` in mock mode returns fixture text for any file, with real checks:
  not a PDF → `415`, over 5 MB → `413`, filename containing `scan` → `422`.
- **Q19** `links` are plain strings without labels; an experience item has no separate location.
- **Q20** An item with every field empty is dropped on save, by the client and by the server.

## Contract changes this implies (for the spec)

- `CvData`: three new blocks (`projects`, `certifications`, `languages`) and `sectionOrder`;
  `QuestionTarget.section` and the fact-verification rules extend to the new blocks.
- `roleNote` → `roleContext`, limit 1 000 → 5 000.
- `PATCH /api/cvs/:id`: `data` optional, client-generated item ids, may skip questions and change
  the status.
- Auto questions follow the required-blocks table (Q17.3) instead of the old fixed field list.
- `docs/architecture.md` §13: mark the confirmed rows; update `docs/uk/` in the same change.
